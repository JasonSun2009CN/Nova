# ADR-0005: 架构风格 - 引擎层与 UI 层严格分离

- 状态: Accepted
- 日期: 2026-07-29
- 决策者: 项目初始团队

## 背景与问题陈述

Nova 的核心复杂度在于两个完全不同的领域：
1. **物理/计算引擎**：相对论计算、航线规划、星空渲染、时间膨胀、轨道力学。这些逻辑是纯计算（或纯 WebGL 绘制），**与 React 无关、与 DOM 无关**。
2. **用户界面**：星图导航 UI、航行仪表盘、设置面板、航行日志等，需要 React 状态管理和 DOM 交互。

如果不做严格分层，容易出现「React 组件里直接写物理计算」「渲染循环触发 React re-render」等问题，导致性能下降、调试困难、单元测试难以编写。

## 考虑过的方案

### 方案 A: 严格分层架构（引擎层独立 + 适配层 + UI 层）

```
┌───────────────────────────────────────────────────────┐
│                     UI 层 (React)                     │
│  Pages / Components / Hooks / Store (Zustand)          │
└──────────────────────┬────────────────────────────────┘
                       │  适配层：Hooks + Store Actions
┌──────────────────────▼────────────────────────────────┐
│                  引擎层 (Pure TS / No React)           │
│  ┌──────────┐ ┌────────────┐ ┌──────────┐ ┌─────────┐ │
│  │ Physics  │ │ Navigation │ │ Renderer │ │  Data   │ │
│  │ (相对论)  │ │ (航线规划)  │ │ (WebGL)  │ │ (星表)  │ │
│  └──────────┘ └────────────┘ └──────────┘ └─────────┘ │
│  ↕ 对外暴露：纯函数 / Class 实例 / EventEmitter        │
└───────────────────────────────────────────────────────┘
```

**引擎层规则：**
- **0 依赖 React**：不 import 任何 `react`、`react-dom`、`@react-three/*`
- **纯逻辑优先**：所有算法以纯函数形式暴露（输入 → 输出，无副作用）
- **副作用隔离**：WebGL 渲染器、计时器等有状态的部分用 Class 封装，生命周期明确（init / start / stop / destroy）
- **事件驱动**：引擎层通过回调或 EventEmitter 通知状态变化，不直接改 React Store

**UI 层规则：**
- 只通过 `useEngine()` Hook 或 Store Action 调用引擎层
- 禁止在 React 组件中直接写物理公式或 Three.js 渲染逻辑

**优点:**
- 可测试性：引擎层可以在 Node.js 中跑单元测试（无 DOM / 浏览器依赖）
- 可移植性：引擎层未来可搬到 Electron / React Native / WebGPU 上，几乎不用改
- 性能可控：Three.js 渲染循环与 React 渲染循环完全解耦，不会互相阻塞
- 职责清晰：算法同学专注引擎，UI 同学专注界面

**缺点:**
- 初期需要额外写适配层代码（Hook 封装）
- 状态双向同步（引擎 ↔ Store）需要仔细处理，避免不同步 Bug

### 方案 B: React 组件中心化（所有逻辑放组件/Hook）

**优点:**
- 初期开发快，无需考虑分层
- 所有状态在 React 中，调试方便（React DevTools 全可见）

**缺点:**
- 性能灾难：渲染循环里调用 `setState` 会导致 60fps 的 re-render
- 单元测试需要 JSDOM 环境，WebGL 部分几乎测不了
- 算法和 UI 耦合，重构渲染器（如 Three.js → WebGPU）几乎要重写整个项目
- **不适用**：Nova 的物理计算和渲染复杂度远高于普通 CRUD 应用

### 方案 C: 微内核 + 插件系统

**优点:**
- 扩展性最好，每个模块是插件
- 适合 v2.x+ 引入自定义星图、多人联机等功能

**缺点:**
- v1.0 之前属于过度设计，开发成本高
- 调试插件依赖关系复杂
- **结论**：v2.0 之后再考虑，当前阶段不采用

## 决策

采用 **方案 A：严格分层架构**。

## 决策依据

1. **核心资产是引擎**：Nova 的差异化竞争力是「真实宇宙 + 时间膨胀」，这些逻辑是纯算法，应该作为独立资产沉淀，不应与任何框架绑定
2. **性能需求刚性**：航行视图要求 60fps，一旦 React 渲染与 WebGL 渲染耦合，几乎必然掉帧
3. **测试友好**：相对论计算、航线规划是容易出错的模块，需要高覆盖率的单元测试，引擎纯 TS 化后可直接在 Node 中测试
4. **预留未来迁移**：如果未来要做桌面端（Tauri）或移动端，引擎层 100% 复用，只需重写 UI 适配层

## 后果

### 正面影响
- 物理计算代码覆盖率可轻松做到 95%+
- 未来迁移到 WebGPU 或原生 Metal/Vulkan，引擎层的算法代码 100% 复用
- 性能问题容易定位：是引擎慢还是 UI 慢，一目了然
- 团队分工清晰：算法同学和前端同学可并行开发

### 负面影响
- 初学者需要理解「引擎 → 适配层 → React」的数据流，文档要写清楚
- 状态同步：引擎内的「当前位置」与 Store 中的「当前位置」需要单向数据流约定（引擎是 Source of Truth，UI 只读）
- 调试需要同时开 DevTools + 浏览器 Console（引擎日志打 console）

### 风险与缓解措施

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| 开发者不自觉地在 React 里写引擎逻辑 | 中 | 高 | ESLint 规则：禁止 components/ 目录下直接 import from engine/ 内部子目录，只能通过 @/engine/index 暴露的公开 API；Code Review 必查 |
| 引擎状态与 UI 状态不同步 | 高 | 中 | 严格单向数据流：引擎 → EventEmitter → Store Action → React；禁止反向直接修改引擎内部字段 |
| 引擎实例内存泄漏（未 destroy） | 中 | 中 | 提供 `useEngine()` Hook 在 unmount 时自动调用 destroy；编写 ESLint 规则提醒 |
