# ADR-0002: 图形渲染方案 - Three.js + WebGL 2.0 + Inline SVG

- 状态: Accepted
- 日期: 2026-07-29
- 决策者: 项目初始团队

## 背景与问题陈述

Nova 有两类图形渲染需求：

1. **3D 场景**：星图导航、第一人称航行视图、黑洞可视化等需要高性能 3D 渲染
2. **2D UI 图形**：仪表盘、天体图标、航行进度环、成就徽章等需要精细控制和矢量缩放

需要一套兼顾性能、灵活性、开发效率的渲染方案。

## 考虑过的方案

### 方案 A: Three.js (WebGL 2.0) + Inline SVG（混合）

**分工：**

- **Three.js**：3D 星空、星图导航视图、航行第一人称视角、粒子系统、后处理（辉光、景深）
- **Inline SVG**：所有 UI 组件（天体卡片、仪表盘、进度条、图标、热力图）

**优点:**

- Three.js 是 WebGL 生态最成熟的封装，文档和示例丰富
- WebGL 2.0 支持实例化渲染、变换反馈等，可高效渲染数十万颗恒星
- Inline SVG 完美匹配用户对"光学对齐、视觉平衡"的高要求（pixel-level control）
- SVG 天然矢量缩放，支持响应式和高 DPI 屏
- 两种渲染上下文（WebGL Canvas + SVG DOM）可叠加，互不干扰

**缺点:**

- 需要在 Canvas 和 DOM 之间做坐标转换（如点击 3D 恒星弹出 DOM 卡片）
- 两套绘制系统，调试方式不同
- Three.js 后处理（EffectComposer）性能开销大，低端设备需降级

### 方案 B: 纯 Canvas 2D

**优点:**

- API 简单，调试方便
- 2D UI 图形直接绘制，无需 SVG

**缺点:**

- 3D 效果需要自建数学库（透视投影、旋转矩阵），开发量极大
- 恒星点渲染需要手动实现 LOD，性能不如 WebGL 实例化
- 粒子系统、辉光等特效性能差
- **不适用**：项目需要真实的 3D 太空场景

### 方案 C: Babylon.js

**优点:**

- 功能比 Three.js 更全面（内置物理引擎、场景图等）
- TypeScript 原生支持更好
- Playground 调试体验优秀

**缺点:**

- 包体积比 Three.js 大 ~30%
- 社区资源和第三方扩展（如后处理 shader）不如 Three.js 多
- React 集成（@babylonjs/react）不如 R3F 成熟
- 团队成员 Three.js 经验更丰富

### 方案 D: WebGPU（优先于 WebGL）

**优点:**

- 下一代图形 API，性能远超 WebGL
- 对大规模粒子渲染（百万级恒星）有原生优势

**缺点:**

- 2026 年浏览器兼容性仍不全面（Safari 支持滞后）
- Three.js 的 WebGPU 后端目前在实验阶段，可能有坑
- 学习曲线更陡，团队经验不足
- Nova 基础版只需渲染 ~10 万颗恒星，WebGL 2.0 已足够
- **结论**：预留升级路径，但 v1.0 不采用

## 决策

采用 **方案 A：Three.js (WebGL 2.0) 负责 3D 场景 + Inline SVG 负责 UI 图形** 的混合渲染方案。

## 决策依据

1. **需求匹配**：Nova 同时需要高性能 3D 场景（WebGL）和高精度 UI（SVG），混合方案刚好对应
2. **生态成熟**：Three.js + @react-three/fiber + drei 是目前 Web3D 开发效率最高的组合
3. **渐进式复杂度**：v0.1 MVP 可只做简单星空粒子，v0.2 加星图，v0.3 加后处理特效，逐步引入复杂度
4. **用户偏好对齐**：SVG 方案完全契合 memory 中提到的"使用 Inline SVG 处理高性能图形渲染"和"对 UI 视觉对齐和光学平衡有较高要求"
5. **升级路径明确**：未来可平滑迁移到 WebGPU（Three.js 正在原生支持），无需重写业务逻辑

## 后果

### 正面影响

- v0.2 星图即可达到 10k+ 恒星 60fps，v0.3 航行模式的相对论视觉效果有现成 shader 参考
- SVG UI 可完全按设计稿像素级还原，支持主题换肤
- 未来可独立升级 3D 渲染层（如从 WebGL → WebGPU），不影响 SVG UI 层

### 负面影响

- 初学者需要同时理解 Canvas 和 DOM 两套坐标系统
- React 和 Three.js 的状态边界需要严格遵守（见 ADR-0005 架构风格）
- 后处理效果（Bloom、SSAO）在集成显卡上可能掉帧，需要做性能分级

### 风险与缓解措施

| 风险                                       | 影响 | 概率 | 缓解措施                                                                  |
| ------------------------------------------ | ---- | ---- | ------------------------------------------------------------------------- |
| R3F 导致 React 渲染与 WebGL 渲染耦合过深   | 高   | 中   | 严格遵守"渲染对象放 useRef，状态放 Zustand"；避免每帧触发 React re-render |
| 移动端 WebGL 支持差异（iOS Safari 限制多） | 中   | 高   | 做 WebGL 特性检测，缺失时降级渲染效果；优先保证功能可用                   |
| 恒星数据量大导致首屏加载慢                 | 中   | 高   | 分块加载 + IndexedDB 缓存；初始只加载太阳系附近 50 光年数据               |
| SVG 节点过多导致 DOM 重排                  | 中   | 低   | 复杂图表（如热力图）用 Canvas 2D 绘制；大量重复图标用 symbol + use 引用   |
