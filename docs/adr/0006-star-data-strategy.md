# ADR-0006: 星图数据策略 - 分层加载 + LOD + 真实星表

- 状态: Accepted
- 日期: 2026-07-29
- 决策者: 项目初始团队

## 背景与问题陈述

Nova 需要构建一个科学准确的宇宙模型，但面临以下挑战：

1. **数据规模**：完整 Gaia DR3 星表包含 18 亿颗恒星，不可能全部加载
2. **性能约束**：浏览器 WebGL 同时渲染超过 10 万点会明显掉帧
3. **科学准确性**：恒星位置、距离、颜色必须真实，不能纯随机生成
4. **首屏体验**：用户打开应用 2 秒内需看到可用的星图

需要一套兼顾准确性、性能、加载速度的数据策略。

## 考虑过的方案

### 方案 A: 真实星表分层 + LOD + 分块懒加载

**数据分层：**

| 层级 L    | 距离范围               | 数据来源                                | 加载时机                  |
| --------- | ---------------------- | --------------------------------------- | ------------------------- |
| L0 星系   | 本星系群 0-1000 万光年 | 手工整理（~100 个星系）                 | 首屏必载                  |
| L1 深空   | 银河内 500-50000 光年  | 主要星云 / 星协 / 银河结构（~1000 个）  | 首屏必载                  |
| L2 亮星   | 0-500 光年，视星等 < 8 | Hipparcos / Yale Bright Star（~10k 颗） | 首屏必载（压缩后 ~200KB） |
| L3 近邻   | 0-50 光年全部恒星      | RECONS / HIPPARCOS（~1800 颗）          | 首屏必载，含行星数据      |
| L4 太阳系 | 0-100 AU               | JPL DE430 行星星历                      | 首屏必载，实时轨道        |
| L5 扩展   | 50-500 光年全部恒星    | Gaia DR3 近邻子集（~50 万颗）           | 用户缩放/搜索时按需懒加载 |

**LOD 策略（同一视口内）：**

- 距离摄像机 < 10 光年：全部渲染 L3 数据
- 距离 10-100 光年：按视星等过滤，只渲染亮于 6 等的恒星
- 距离 > 100 光年：只渲染 L2 亮星 + L1 深空天体
- 距离 > 5000 光年：只渲染 L0 星系 + 银河投影

**分块策略：**

- L5 扩展星表按 10×10×10 光年立方块划分，每块约 100-500 颗恒星
- 块名使用 Z-order curve (Morton code) 编码，方便按空间距离预取相邻块
- 块数据缓存在 Dexie (IndexedDB)，离线可用

**优点:**

- 科学准确：所有天体都有真实数据支撑
- 首屏可控：必载数据约 500KB gzip，加载 < 200ms
- 可扩展：未来可以逐步加入更大范围星表，不影响首屏
- 性能保证：任何时刻 WebGL 渲染的点不超过 2 万

**缺点:**

- 数据处理 Pipeline 复杂（需要写脚本从 Hipparcos/Gaia 原始数据中预处理 + 分块）
- 空间索引和缓存淘汰策略需要精心设计
- L5 懒加载时，用户快速缩放可能遇到"星星突然冒出来"的跳变

### 方案 B: 纯程序化生成（Procedural Generation）

使用 Perlin Noise / OpenSimplex 等噪声函数按种子生成恒星位置和属性。

**优点:**

- 数据体积 0，无需下载
- 可生成任意数量恒星（按需生成可视范围）

**缺点:**

- **核心背叛**：用户使用 Nova 是想要「真实宇宙」，程序化生成的假恒星毫无意义
- 无法匹配真实导航：用户搜「北极星」找不到，搜「天狼星」位置不对
- **不适用**：完全违背产品定位

### 方案 C: 固定精选集（只放几百颗著名恒星）

**优点:**

- 开发最快，数据量最小

**缺点:**

- 星空空旷，缺乏「浩瀚感」
- 用户熟悉的大多数恒星不在列表中
- 很快探索完，没有长期激励
- **不适用**：作为 v1.0 之前的 MVP 临时方案可以，但长期不行

## 决策

采用 **方案 A：真实星表分层 + LOD + 分块懒加载**。

v0.1 MVP 阶段可先用方案 C 固定精选集（~100 颗亮星）跑通流程；v0.2 星图阶段升级到完整方案 A。

## 决策依据

1. **产品核心价值**：Nova 的灵魂是「真实宇宙中的星际旅行」，真实星表是不可妥协的底线
2. **分层渐进加载**：既保证首屏体验（必载数据少），又支持用户深入探索（扩展星表按需加载）
3. **科学可验证**：恒星位置、距离、光谱型与真实数据一致，天文爱好者可以「验真」，提升产品可信度
4. **性能上限清晰**：LOD + 分块控制渲染点数量 ≤ 2 万，主流设备稳 60fps

## 后果

### 正面影响

- 「真实感」是最大的产品差异化优势
- 扩展星表可以作为 v1.x 版本的迭代内容，保持用户新鲜感
- 数据 Pipeline 一次搭建，后续 Gaia 新版本数据可复用流程

### 负面影响

- 前期需要投入 1-2 周开发数据预处理脚本（Python/Node）
- 星图缩放时的跳变需要做「渐入渐出」过渡动画，减少突兀感
- 离线时扩展星表仅能访问已缓存的块

### 风险与缓解措施

| 风险                                            | 影响                 | 概率 | 缓解措施                                                               |
| ----------------------------------------------- | -------------------- | ---- | ---------------------------------------------------------------------- |
| 数据预处理脚本产出的星表有错误（坐标/距离不准） | 天文爱好者发现后差评 | 中   | 抽样 100 颗亮星与 SIMBAD 数据库交叉验证；自动化测试对比已知距离        |
| L5 懒加载时闪屏/跳变                            | 用户体验差           | 高   | 新加载的点在 1s 内从透明渐入；对邻接块做预取（预测缩放方向）           |
| 星表数据版权限制（Gaia 是 CC-BY-SA）            | 法律风险             | 低   | Gaia/HipparCOS 数据均为开放协议，在关于页注明数据源即可                |
| IndexedDB 缓存占满磁盘                          | 中                   | 低   | LRU 淘汰策略：最近 30 天未访问的块自动清理；设置缓存上限（默认 200MB） |
